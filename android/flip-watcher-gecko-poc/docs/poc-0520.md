# 0.5.20: known notification overlay, ordinary Close only

Samsung0.5.19 still shows a milky page and blocks manual swipes. The readiness
race fixed in0.5.19 was real, but did not resolve the reported physical symptom.

Mozilla bug1926869 documents the same distinctive pattern: Facebook desktop on
Android, translucent light backdrop, tiny Close at top-left, a notification
notice with role=alertdialog and aria-label=Push notifications request.
Source: https://bugzilla.mozilla.org/show_bug.cgi?id=1926869 (comments13,21,22).
This is a documented compatibility failure, not proof of the phone's actual DOM.
Our existing modal gates handled role=dialog and missed role=alertdialog.

After fresh desktop-preview consent and confirmed same-group context, the new
isolated-content helper checks bounded visible modals. It may invoke the ordinary
DOM Close button ONCE only for the exact known notification notice (limited
English/Polish labels). It requires one modal and one visible, enabled Close or
Zamknij button with an unobstructed center hit. Forms, inputs, links, embedded
frames, article/feed-owned dialogs, external form bindings, oversized/ambiguous
subtrees and any other action are rejected. The node is checked again immediately
before acting. The click is normal DOM click, not forged trusted input.

No notifications are granted or permissions changed. No notification API is
patched. No CSS is overridden and no page nodes are removed by our code. The
page's own Close handler must dismiss its own notice within1500ms and within the
original deadline; otherwise NOTICE_BLOCKED stops with no rows. Unknown alerts,
CAPTCHA/login/checkpoint and other modals are never closed. Any later modal
revokes the trial instead of permitting scrolling behind it. Modal guards in
both gesture and native viewport now include alertdialog.

Fresh native consent explicitly describes closing this one ordinary notice,
without enabling notifications. Fixed private NOTICE hint shows the action.
Two boolean counters, noticeDetected/noticeClosed, join the count-only protocol;
closed cannot exceed detected. Prior80-counter summaries are read with two zero
values in RAM without rewriting history. STOP for a blocking notice retains only
validated counters, never rows or full content. Core parsing, filters, photo mode,
30s/20ID/60s limits and all production isolation remain unchanged.

Regression fixture mirrors the documented DOM pattern, hidden helper text and
milky backdrop, with pointer-blocked content and tiny Close. An actual Android
InputManager swipe must fail before Close. After new consent/reload, the ordinary
Close action must remove the fixture mask, then a real window swipe must anchor
the long content pane and automatic scrolling must reach >=25 moves and a NEW
exact offer. Unknown security-like alert variant must remain untouched and STOP
before any gesture. Before/after screenshots contain ONLY this local fixture.

Node covers missing consent/context, unknown alerts, unsafe/ambiguous/covered
buttons, replacement, expiry, ineffective Close, navigation, late-modal cleanup
and absent helper. JVM covers strict boolean counters,80-field history and
row-free blocked replies. Full CI results and APK link are recorded in PR45.
The workflow first runs the2 new regression methods and then ALL Android tests,
avoiding a redundant repeat of the entire slow desktop class.

Install only as an update with the existing debug signer; never uninstall/reset.
Leave default gesture on and images off. The report must show notification
counts, then the normal operator gesture after TERAZ. Unknown/late overlays
STOP; do not infer success from a conditional offer verdict alone. A real Samsung
confirmation is still required. No agent login/real Facebook scan, collector,
upload, production configuration, merge or deployment is performed.
