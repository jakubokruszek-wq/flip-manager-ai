# Gecko POC 0.3.5 — Beacon: wynik NO_GO

Samsung 0.3.4 potwierdził 14 Beacon w pozostałych /ajax, EligibleBeacon=14, bez XHR/fetch/other. To nie dowodzi obecności danych postów w odpowiedziach. Podczas próby dodania osobno zatwierdzanego odczytu test rzeczywistego GeckoView ujawnił, że filtr kończy się bez bajtów nawet dla endpointu z niepustą odpowiedzią.

## Dowód i ograniczenie

Test kontrolny pobiera dokładny lokalny endpoint przez niezależny HTTP GET i sprawdza niepuste fixture zawierające dokładne testowe ID. Następnie ta sama strona/endpoint odpowiada na prawdziwy navigator.sendBeacon bez payloadu (eliminuje problem nieodczytanego ciała POST w prostym serwerze fixture). StreamFilter zgłasza Completed, ale nie otrzymuje żadnych bajtów i nie ma ID. Osobny pusty endpoint daje ten sam rezultat. Nie jest to dowód pustej odpowiedzi na serwerze.

Kod Mozilli wyjaśnia mechanizm: [BeaconStreamListener::OnStartRequest](https://github.com/mozilla-firefox/firefox/blob/main/dom/base/Navigator.cpp#L1194) zwraca NS_ERROR_ABORT; OnDataAvailable zawiera MOZ_ASSERT(false). Aktualne źródło upstream potwierdza mechanizm; regresja na naszym GeckoView 158 jest niezależnym dowodem działania konkretnej wersji. Nie obchodzimy tego zachowania silnika.

Pierwszy test wymagający ID z Beacon celowo nie przeszedł i ujawnił błędne założenie. Końcowy test jest regresją NEGATYWNĄ z niezależnym HTTP control, a nie testem deklarującym działający odczyt Beacon. Testy symulowane Node mogą sprawdzić parser i ochrony, ale nie potwierdzają dostarczenia bajtów w rzeczywistym GeckoView.

## Zablokowane w zwykłej aplikacji

Nie wydajemy nieskutecznego przycisku odczytu Beacon do użycia na prawdziwej grupie. W aplikacji jest wyłącznie przycisk informacyjny **Beacon: wynik NO_GO**; nie otwiera grupy, nie czyta danych i nie uruchamia skanu. Nie trzeba wykonywać kolejnej próby Beacon na Samsungu.

Eksperymentalny odczyt pozostaje wyłącznie w lokalnych fixture: natywny kanał odrzuca beaconConsent poza fixtureMode, a moduł JS wymaga osobnej zgody, flagi fixture i źródła http://127.0.0.1. Prawdziwy kontekst Facebooka nie aktywuje go nawet z flagami true. Zwykłe przyciski 0.3.4 i wszystkie dotychczasowe limity/STOP pozostają. Bez payloadów żądań Facebooka, nagłówków, cookies/tokenów, dokumentu HTML, pingów, /data lub innych typów poza wcześniejszym zakresem.

79 allowlistowanych ograniczonych liczników. Linia **Odczyt Beacon**: Read, Filtered, Completed, Bytes, NoData. W zwykłej aplikacji Read=0. NoData oznacza ukończony filtr bez DOSTARCZONYCH bajtów, nie potwierdzenie pustej odpowiedzi serwera. W eksperymencie komunikat **BEACON BEZ DOSTARCZONYCH BAJTÓW** wyraźnie zaznacza to ograniczenie. Wyłącznie RAM/liczniki; bez raw treści/ID/adresów w raporcie, zapisu lub uploadu. Niezmieniony parser komputerowy, bez zgadywania ID.

## Dostarczenie i dalszy kierunek

APK arm64 i wyniki CI w Draft PR #45. Instalacja opcjonalnie jako aktualizacja bez odinstalowywania/kasowania danych; ten sam pakiet/podpis i wyższy versionCode. Przy konflikcie podpisu przerwij. Instalacja nie odblokuje odczytu Beacon ani kolektora.

PASS testów oznacza odtworzenie i zabezpieczenie ograniczenia oraz zachowanie wcześniejszych funkcji, nie sukces pozyskiwania postów. **NO_GO dla architektury pozyskującej posty z odpowiedzi Beacon przez ten StreamFilter. NO_GO do kolektora/LIVE.** Nie ma podstaw, by prosić operatora o dalsze powtarzanie tej samej próby. Nie deklarujemy pracy pod blokadą.

Dalsze osobne ścieżki to jawny permalink udostępniony przez operatora albo świadomie zatwierdzona analiza innego źródła (np. dokumentu grupy). Odczytu dokumentu nie włączono; dotychczasowa zgoda go nie obejmuje. Nie odczytujemy payloadów Beacon jako obejścia.

Brak zmian produkcji/PR #44, historii/outboxa/limitu starego skanu, wspólnego core, backendu, merge/deploymentu/płatnych usług i prawdziwego skanu przez agenta. Wszystkie próby CI wyłącznie loopback fixture.
