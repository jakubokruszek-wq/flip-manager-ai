# POC 0.5.27 — SVG photo anchor URL type

Physical 0.5.26 report: 47/48 movements in 30 seconds, 20 exact IDs, 6 offer candidates, but zero photo sources/crops. The 73 link and 174 size rejections are repeated observations, not distinct photos. These counts do not identify the rejected URLs or prove that all rejected nodes are listing images.

Reproduced a concrete DOM API gap independently: SVGAnchorElement.href is SVGAnimatedString, while photo extraction previously passed it directly to URL parsing as if it were an HTML string. A valid numeric photo link then produced no source. The local photo adapter now reads the animated string (or legacy base value), resolves relative URLs against the current document, and revalidates the current value before capture. Blank animations and arbitrary object coercion are refused. Existing exact numeric photo/group identity, opaque-wrapper network proof, foreign/profile rejection, dimensions, readiness, occlusion, crop limits and consent gates remain intact. No threshold was lowered.

No scrolling, viewport or network-response code was changed. Same automatic 500ms/30s/up to60 attempts,20-ID/shared60s limits. No new media requests, persisted URLs/content, OCR, upload, active collector/pilot, production changes, merge or deployment. This resolves a verified compatibility bug; it does not establish that SVG anchors are the only cause of the physical report.

Validation: regression fails before the fix (0 sources instead of1), passes after. Node suite418 PASS. A new real-GeckoView fixture uses actual SVGAnchorElement links around red/green image nodes and must show both real colored crops, offer fields, Offers images, RAM recycling and further automatic scroll. Existing fixtures remain in the complete API36 suite. Final JVM/emulator/APK results are in PR45.
