# Gecko POC 0.5.48 — functional selective Story extraction

## Problem and resulting behavior

Physical 0.5.47 reported two blocks over 512 KiB, byte-budget exhaustion and zero records from the one parsed block. Source inspection also showed the pinned parser walks only eight levels deep. A Relay payload can therefore contain an exact post yet be skipped for size or return zero because the Story lies deeper in the wrapper. The agent cannot assert the exact phone payload shape from counters alone.

The detail adapter now selects a bounded, root-owned Story projection before calling the unchanged collector-core. It lexes JSON without JSON.parse of the entire payload, tracks object/array/string/escape boundaries and all ancestor contexts, and preserves the direct numeric Story ID plus an actual exact permalink from the same safe ownership boundary. Source message text must be a direct message/text/body value, its immediate text child, or a message from a same-ID nested Story. Same-owner content/timestamp sections can contribute a message/permalink to their own enclosing Story. Neighboring Story text cannot fill missing own text. No ID/permalink is derived from the requested URL, a photo ID, text, document order or an unverified alias.

Only the small selected ID/permalink/type/message JSON reaches the pinned parser; parser output still passes the existing exact group/post/link/shared-path checks and field projection. Original large payloads do not enter the expensive structured parser. Tracking queries on an actual structured permalink can be removed while preserving its verified group/post path; comment/reply queries and any fragment remain rejected. Native expected-navigation URLs remain strict and unchanged. Media/author fields are not copied by this selector; this release targets property text data. Existing DOM-card and legacy small-JavaScript paths remain; ordinary JSON takes the context-aware selection path instead of losing ancestor ownership in a shallow walk.

## Boundaries and work limits

Pure JSON must validate completely before projections can be accepted. Duplicate keys, malformed strings/escapes, trailing junk and incomplete documents discard projections. Comment/feedback/shared/quote/attachment/media/caption ancestors are excluded; foreign Story ancestors and parent permalinks discovered after the target subtree also reject it. Serialized Story-looking text inside a caption cannot become a root record. Context/fresh consent/focus/login/checkpoint gates are unchanged.

New flat-screening cap: 8,388,608 UTF-16 source characters per reply, at most 4,194,304 characters structurally inspected, maximum depth 128, 20,000 containers/members and eight selected projections. Selected parser input is at most 131,072 characters each; each source message is at most 20,000 decoded characters. The existing 500-ms work deadline, 64 parser calls and 2-MiB projected/legacy parser-input budget remain. These are character budgets consistent with prior JS length-based accounting, not claims of encoded network bytes. Flat source scanning replaces constructing a giant object graph; this is a deliberate bounded source-read extension, not unlimited parsing. Truncation/time/depth/source exhaustion is explicit. A text-bearing own projection can replace a textless duplicate at the candidate cap.

Navigation-only blocks carrying a target URL do not consume the structural Story budget. Cheap identity-key hints are scheduling only; JSON grammar, ownership and exact source ID/permalink must still pass. Two large blocks, including a large navigation block before the real Story data, are regression-tested.

Count-only evidence adds selected source blocks/stories, parser records from projections, rejected contexts, incomplete-selection flag and source characters in units of 1024. Strict native evidence supports the old 12/20/27/42-key schemas and new exact 48-key map. sourceKiB is at most 4096; flags remain 0/1 and count histories remain bounded at 4096 characters. Raw scripts, messages, IDs and source projections are never persisted/exported in reports.

## Verification and Samsung use

Regressions cover real-parser field recovery from a large, deeply nested Relay fixture that the old parser returns empty; two large blocks; navigation-only byte pressure; small deep JSON; same-owner sections; comments/quotes/shared/attachments; foreign IDs and late foreign/opaque-parent links; malformed and duplicate-key JSON; serialized caption text; escaping/unicode; depth/deadline/source limits; textless candidate pressure, neighboring-text rejection and tracked-vs-comment permalink handling. Full Node/JVM/isolation/app and instrumented-source compilation run in CI. Long emulator execution is skipped per user preference; physical Facebook success is not asserted from fixture tests.

Install as an update without uninstalling, run a fresh group preview, then Offers → OCR + uzupełnij brakujące dane. The combined local OCR/opening flow and per-post manual button remain. This is a functional recovery change, not another counter-only build; actual payloads outside the documented evidence/limits can still remain unconfirmed. One approved group and no production scan, upload, collector activation, merge or deployment. Existing scan quota/history/outbox unchanged.
