# Gecko POC 0.4.3 — changed address requires a fresh real load

## Physical evidence and limits

Samsung 0.4.2 reported STOP / LOCATION_WITHOUT_REQUEST, requests 1/8, IDs 0.
The reported address passed the destination grammar but differed from the last
accepted request. This can be the same share token on another allowed Facebook
host/trailing-slash form, or an exact post address of the approved group. The
count-only report does not distinguish these, prove history.replaceState was
used, or prove a server redirect occurred.

MDN documents that replaceState changes the address without fetching or checking
the destination: https://developer.mozilla.org/en-US/docs/Web/API/History/replaceState
Consequently an address change by itself is not accepted as redirect proof.

## One bounded address recheck

A NEW explicit consent now describes one possible native re-opening of a candidate
address in the existing session. Default resolver mode remains strict/off. The
UI enables the option only in a new explicitly consented attempt.

A mismatch can queue only the same share token or an exact permalink of the
approved group on the existing HTTPS Facebook host allowlist. No query/fragment,
credentials, photo IDs, guessed IDs, foreign groups or unverified numeric aliases.
A gesture or unexpected request stops the attempt. Queuing never confirms an ID
or allows content inspection. A native claim is consumed exactly once, then an
actual matching load request must occur. Any second unrequested address change
stops. Same original 20 s / 8 requests, no retry or extension of time.

The recheck waits for the first page to finish within the same deadline, so it
does not cancel that load or ignore its errors. Before issuing the load, the app revokes the old guard, records the private-port
connection generation and wall-clock boundary in RAM, and resets progress.
Confirmation requires a newer trusted top-frame port, matching native address,
fresh nonce, safe complete document and performance.timeOrigin newer than the
boundary. The isolated module returns only a fresh boolean, never the epoch.
Missing/invalid/older metadata cannot arm a guard or confirm a result. Browser
clock precision or clock changes can fail closed; they are not bypassed.
Verification/login markers still STOP, including on an older document.

EXACT_APPROVED_ADDRESS_RELOADED explicitly means the address was loaded and checked
in a new document. It does NOT prove the share link maps to that post, that a post
exists, or that the page contains a complete offer. It cannot authorize a collector
or produce an offer record. Strict HTTP-redirect path retains its separate reason.

The four-field persisted result format remains status/reason/counts only. The new
confirmation reason requires at least two actual requests. No URL, post ID, text,
cookies, token, epoch, nonce or consent is persisted or uploaded. Existing scan
limit/history/outbox/profile/signing key remain intact.

## Regression verification

11 new JVM tests cover candidate-only state, native claim, real request, strict
mode, duplicates, gesture/window/wrong requests, foreign/alias/fake IDs, replay,
budget/deadline/pause, same-token canonicalization and report validation.
3 new Node tests cover stale/missing/malformed/future document metadata and
boolean-only fresh proof. Existing consent/context/verification regressions remain.

New Android16 scenario uses a real local HTML page with history.replaceState.
Before re-opening, the server has received zero requests for the final URL and the
resolver cannot confirm. After the native load, exactly one final-page request,
a new port and fresh document are required. A future freshness boundary is rejected
on the actual Gecko page. Runs focused first, then the full emulator suite.
No job or agent opens Facebook. CI results are maintained in PR45.
